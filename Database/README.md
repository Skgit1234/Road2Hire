# Road2Hire database

This directory documents the PostgreSQL schema used by the backend. The application uses SQLAlchemy models in `Backend/Models/` and Alembic migrations in `Backend/alembic/`; it does not define a separate database implementation here.

## Overview

The database has seven application tables:

| Table | Purpose |
|---|---|
| `users` | User accounts and unique login email addresses. |
| `resumes` | Uploaded resume metadata owned by a user. The file contents live in backend storage, not in this table. |
| `candidate_profiles` | The latest extracted profile snapshot for a user, including skills and resume sections. |
| `pipeline_runs` | One record per AI pipeline execution, with lifecycle state, summary fields, errors, and the complete canonical result in JSONB. |
| `skill_gaps` | A one-per-run summary of occupation and skill coverage metrics. Detailed AI output remains in `pipeline_runs.canonical_output`. |
| `learning_tasks` | Mutable status and progress for roadmap items generated by a pipeline run. |
| `jobs` | User-owned occupation targets and their user-supplied skill requirements. This table does not represent live external job listings. |

## Relationships

- A user can own many resumes, pipeline runs, and jobs. Deleting a user cascades to these rows.
- A user has at most one candidate profile (`candidate_profiles.user_id` is unique). The profile may have no resume (`resume_id` is nullable); deleting its resume through the API preserves the profile and sets `resume_id` to `NULL`. The ORM relationship has no `delete-orphan` cascade, and the foreign key uses `ON DELETE SET NULL`.
- Each pipeline run belongs to one user and one resume. A composite foreign key on `(user_id, resume_id)` ensures the resume belongs to that same user. Deleting a referenced resume is restricted while a pipeline run exists.
- A pipeline run has zero or one skill-gap summary (`skill_gaps.pipeline_run_id` is unique); deleting the run cascades to its summary.
- A pipeline run can have many learning tasks; deleting the run cascades to those tasks. `(pipeline_run_id, logical_item_key)` is unique.
- The database foreign key from `candidate_profiles.resume_id` is nullable and not unique, so the database does not guarantee a one-to-one profile-to-resume relation or that the referenced resume belongs to the same user. The ORM exposes `Resume.candidate_profile` as scalar, but that cardinality is not enforced by the database. Deleting a resume through `Backend/Api/resume.py` preserves its profile and clears the nullable foreign key.
- `jobs.user_id` has a foreign key to `users.id`. There is no corresponding `User.jobs` ORM relationship in the current models.

See [ER_DIAGRAM.md](./ER_DIAGRAM.md) for the relationship diagram.

## Source of truth

The migration chain currently has one head: `a41c9e76bd20` (jobs), after `8f60453d5a04` (pipeline-run and roadmap redesign). [`schema.sql`](./schema.sql) is a reference snapshot of the application tables at that migration head; it is not a replacement for Alembic and should not be used to initialize or update a deployment independently.

The SQLAlchemy models define application mappings and ORM-side defaults. Alembic migrations define the database DDL actually applied. The schema reference follows the migration DDL. There are a few differences to keep in mind:

1. The migration gives `jobs.required_skills` a PostgreSQL server default of `[]::jsonb`; the model defines only a Python-side `default=list`. Database inserts that bypass SQLAlchemy therefore receive a default that is not represented as a model server default.
2. The migrations name the unique constraints on `users.email` and `candidate_profiles.user_id` (`uq_users_email` and `uq_candidate_profiles_user_id`). The models mark those columns `unique=True` without specifying those names. The uniqueness rules match, but the constraint names do not.
3. `onupdate=now()` on model timestamp columns is applied by SQLAlchemy during ORM updates; the migrations do not create database triggers that update those columns for direct SQL updates.
4. `candidate_profiles.resume_id` is not unique and has no composite ownership constraint, despite the scalar ORM relationship. Resume deletion through the API preserves the candidate profile and sets this column to `NULL`, consistent with the migration's `ON DELETE SET NULL` constraint. See the relationship notes above.

No user data, passwords, JWT secrets, or seed records are included in these documents. Alembic also maintains its own `alembic_version` bookkeeping table; it is not one of the seven application tables in the reference schema.
